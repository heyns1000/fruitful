Prefaceiv
Preface

Why this exists

Most of what fills a working session like this one never gets bound into anything. It lives as a scroll of turns, a folder of drafts, a dozen open tabs each arguing that it's the current version of the truth. That's fine for building — it's exactly how building works — but it's a poor way to keep something. A palette gets rediscovered instead of remembered. A rule gets restated slightly differently each time it's needed. Eventually nobody, including the person who built it, can say with confidence which document is the one that's actually correct.

This book is the answer to that, for one ecosystem, at one point in time. It takes eleven documents — a brand guide, an icon application, an ecosystem index, a product page, a manual, a debrief written for the next person to pick this up cold, a full excavation of a live repository, a video treatment that was never filmed, a copyright letter, a game, and a builder's own profile — and binds them into a single object with a spine. Not because a coffee-table book is how software usually gets documented, but because the alternative, scattered across however many browser tabs, was never going to survive contact with a year from now.

Every page that follows was re-read from its source before it was set here — not summarized from an earlier conversation, not reconstructed from what seemed likely to be true. Where a document had already corrected itself once — and one of these, the Debrief in Chapter VI, corrects a wrong palette in its own second paragraph — that correction is preserved exactly as it stands, because getting something wrong once and saying so plainly is itself part of an honest record.

What holds these eleven very different documents together is not a shared subject in the usual sense — a brand guide and a database excavation don't normally belong on the same shelf, and a copyright letter belongs to neither. It's a shared discipline: each one draws a hard line between what has been verified against a real file and what has only been claimed. The Seedwave Atlas in Chapter III makes that discipline explicit with a five-colour legend — live, draft, planned, reference, archived — and refuses to promote a plan to a fact just because it would be convenient. That refusal, more than any single palette or diagram, is the actual subject of this book. Part Five closes it the other way round: after ten chapters of systems, the last three are simply the people the systems are for.

— compiled from the seven repositories currently in reach, for Heyns.

The Connector

"Your store relays. The Worker decides." A thin, signed WordPress client that holds no payment credentials, no brand assets, and no opinion of its own — every order event and every brand colour comes from one place.

verified source · v5.1.0 product page
The Connector36

Two jobs. One connector.

Both run through the same thin client, the same signed channel, and the same rule: nothing sensitive is ever stored twice.

01 · Commerce sync — WooCommerce → WorkerOrder status changes relay over a signed channel. HMAC-SHA256, constant-time verified; idempotent by event ID; a terminal order never moves backward.
02 · Brand alignment — CI Guide → themePalette and icon rules are fetched live from the Worker and printed as CSS custom properties on every page. Public, unauthenticated, read-only; cached an hour; a silent no-op if unreachable.

Architecture — how a thin client stays thin

The plugin makes exactly one kind of outbound call — to the Worker. It never talks to Paystack, BobGo, GitHub, or Google Drive directly; those live exclusively behind it.

The Worker is the only thing that ever sees a Paystack key, a BobGo credential, or a GitHub token.

The Connector40

Security — not an afterthought, a rewrite

Version 5.0.0 replaced the previous 4.7.x line rather than patch it.

  • Fails closed on a weak key. A missing, short, or default-placeholder AUTH_KEY means the plugin refuses to store or use a secret — not a predictable fallback.
  • No secret reaches the browser. The rewrite is server-side only, nonce-protected, and never echoes a secret.
  • Inert without WooCommerce. The commerce bridge registers zero hooks when WooCommerce isn't active.
  • Constant-time signature checks. HMAC-SHA256 over the raw body, compared without leaking match progress through response timing.

Install — four steps, no guesswork

  1. Set the shared secret on the Worker — wrangler secret put WP_BRIDGE_SECRET.
  2. Configure the plugin — Banimal™ → Configuration: Worker base URL and the same signing secret.
  3. Confirm the connection — Banimal™ → Diagnostics: "Check Worker Health" and "Check Brand Guide," both live, never cached.
  4. Change an order status — confirm a row lands in wp_bridge_events.
// what the plugin sends — nothing more
{
  "event_type": "woocommerce.order_status_changed",
  "schema_version": "1.0",

FAQ

Do I need WooCommerce to use this plugin?

No. The brand module works on any WordPress site. The commerce bridge simply does nothing until WooCommerce is active.

Is the brand-guide endpoint safe to call from anywhere?

Yes — public and unauthenticated by design. Palette and icon rules aren't secrets; only order events require signing.

What happens if Sam Fox revises the CI Guide?

Update the guide and the matching Worker route. Every connected WordPress site picks up the change within an hour — no plugin update required.

Can I use this outside the Banimal™/Fruitful ecosystem?

The commerce bridge is specific to this Worker. The brand-guide pattern — pull tokens and an icon from one endpoint — is general, and exactly what a future non-WordPress adapter would reuse.

Inconsistencies worth knowing before dispatch

Nothing here was fixed at the time this excavation was written — each one only touched files outside that day's actual task.

high
Two different giving rates for the same thing

The real rate computed as 0.1501 (15.01%). A separate checkout-path insert hardcoded 0.02 with the comment "// 2% giving" — a live, uncorrected contradiction.

high
Three order-reference formats for one concept

BAN-<nanoid>, TXN_<nanoid>, WC-<wc_order_id> — three ID schemes for what the schema treats as one orders table.

medium
Session tokens weren't signed

Issued as btoa(JSON.stringify({...})) — trivially forgeable, not a JWT. The code's own comment: "in production use a signed JWT."

medium
Coupon usage counters didn't persist

Tracked on a module-level object in memory — every Worker isolate restart reset every code's usage count to zero.

medium
Domain split between .co.za and .faa.zone

SEO surface targets one domain; transactional email templates link to the other. Both are live CORS origins, so neither is obviously wrong — but a customer following an email link lands somewhere different from what Google indexes.

Every figure in this chapter traces to a specific file in the repository — nothing here was recalled from memory. Several of these findings were the actual work items closed out later in this same ecosystem's history — the giving-rate contradiction and the unsigned session tokens both among them.
